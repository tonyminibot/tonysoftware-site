Building Skyline: an on-device boarding-pass scanner with Apple Intelligence

Every flight tracker app I've used wants my email, an account, and a server to call. Skyline doesn't. You take a photo of your boarding pass; the iPhone parses it; the flight shows up on a 3D globe. Nothing leaves the device. Works in Airplane Mode. No login screen exists.

The hard part — and the part I want to write up — is how the parsing actually works. Boarding passes come in three flavors (photo of paper, screenshot of mobile, PDF in Wallet) and three formats (BCBP barcode that's machine-precise, OCR-able text that's noisy, sometimes both, sometimes neither readable). Apple Intelligence is great when it's there. It's not there on every device. The IATA barcode is ground truth but only if you can decode it.

So Skyline runs a three-tier extraction pipeline with a deterministic merge step. Below is how it's structured. Skyline is free on the App Store; the full Xcode source is $19 on Polar if you want to fork it for a different vertical.

The three tiers

The pipeline runs in this order on every captured image:

  1. Vision OCR + on-device Foundation Models — the primary parser. Takes the OCR text, prompts the on-device LLM to extract {airline, flight#, from, to, date, seat, class, name} as structured JSON.
  2. PDF417 / QR barcode → IATA BCBP decode — deterministic machine data. Used to verify and correct the AI result on the four identity fields (airline, flight number, route, date). The barcode is ground truth.
  3. Heuristics — regex-on-OCR-text fallback for when Apple Intelligence isn't available on the device (older hardware) or returns too little.

If everything fails, the user still gets whatever was extracted and can edit + save manually. The pipeline never refuses to return a result.

Why three tiers and not one

Each tier on its own has known failure modes:

  • AI alone: hallucinates plausible-but-wrong flight numbers when the OCR text is ambiguous (BA42 vs BA420 vs B447). Fast on Apple Intelligence devices, unavailable on older ones.
  • Barcode alone: 100% accurate when readable, but mobile screenshots often crop the barcode out, and photo-of-paper boarding passes have variable scan quality. ~40% of real-world boarding passes I tested had no decodable barcode.
  • Heuristics alone: works for ~70% of standard layouts. Falls apart on regional carriers with non-Latin script or unusual layouts.

Composed: barcode overrides the AI result on the four identity fields when present + decodable. AI fills in the rest (seat, class, passenger name — barcode has some of these but not reliably). Heuristics are the floor when nothing else works.

The merge rule

The merge logic is the actual interesting piece. Most pipelines either "use the first available result" (loses information) or "use the most recent" (loses ground truth). Skyline uses a field-level merge with explicit precedence:

// Priority per field:
// airline, flight#, route, date  →  barcode > AI > heuristic
// seat, class, name              →  AI > barcode > heuristic
// any field not yet filled       →  pull from next-best tier

Two parsers agreeing isn't required. One parser providing high-confidence data is enough. The pipeline only refuses to commit when ALL three return empty.

Why Apple Intelligence (not a cloud LLM)

The first design decision was: do I call OpenAI / Anthropic / Gemini, or do I use the on-device model?

Cloud LLM means: an API key (mine or BYOK), a server (mine or proxy), latency (200-800ms per parse), cost (cents per parse × N users), privacy concerns (you're sending the user's flight history to a third party), and fragility (model versions change, prompts drift). For a one-shot extraction that runs ~5 times a year per user, the cloud cost is fine. Everything else is friction.

On-device LLM means: zero network calls, zero per-call cost, zero leaked data, ~100-300ms parse time on iPhone 15 Pro+, and the obvious downside — only works on Apple-Intelligence-eligible devices (iPhone 15 Pro and newer + M-series iPads as of iOS 26).

The availability check is one variable:

static var isAvailable: Bool {
    #if canImport(FoundationModels)
    if #available(iOS 26.0, *) {
        return SystemLanguageModel.default.isAvailable
    }
    #endif
    return false
}

The pipeline simply skips the AI tier when it's not available. The fallback heuristic + barcode tiers still work on older devices; you just lose the high-quality OCR-to-structured-data step. Skyline's MIN-iOS is the FoundationModels minimum so the rest works everywhere.

The 3D globe

Once a flight is saved, it pins as a glowing great-circle arc on a SceneKit 3D Earth. Night-side lights are baked into the Earth texture; great circles are computed from the lat/long pairs and drawn as parametric curves on a transparent overlay layer. The globe spins slowly on idle; pinch-zoom shows individual airport pins.

There's nothing exotic in the SceneKit setup. The interesting bit is keeping it 60fps on a phone: pre-compute all flight arcs at load time, throttle the rotation animation to 30fps when there are >50 flights, and use SceneKit's level-of-detail to swap in a lower-poly Earth mesh on iPhone 12 and older.

What's offline

Everything. Airport database (6,000+ entries) ships in the app bundle as a compressed JSON. Boarding pass parsing is on-device. Globe rendering is local. The only network call in the entire app is the App Store rating prompt's metadata fetch, which is Apple's API and runs on the system schedule.

This isn't a marketing tagline. The "Airplane Mode" use case — open the app on the plane, see your past flights, look at the route you just took — was the original design constraint. If anything reaches the network, the design failed.

SwiftData for the log

Every parsed flight is saved to SwiftData. The model is one class (Flight) with the obvious fields. Search uses SwiftUI's native .searchable with a custom predicate that matches airport codes, airline names, dates, and free-text. Sort is by creation date descending by default (a recent fix from beta feedback — was alphabetical, which made no sense).

File structure

  • App/ — SkylineApp + RootView with the 3-tab structure (Globe / Capture / Settings).
  • Features/Capture/ — Camera + photo library + multi-import flow.
  • Features/Globe/ — SceneKit 3D Earth + great-circle arc renderer.
  • Features/History/ — Searchable flight list + filters.
  • Features/FlightDetail/ — Per-flight view with airport context + Save-to-Photos.
  • Features/Review/ — Edit-before-save sheet for low-confidence parses.
  • Features/Onboarding/ — 3-step intro.
  • Services/BoardingPassPipeline.swift — the orchestrator described above.
  • Services/AIExtractor.swift — Apple Intelligence wrapper.
  • Services/BCBPParser.swift — IATA BCBP M1/M2 barcode decoder.
  • Services/HeuristicExtractor.swift — regex fallback parser.
  • Services/BoardingPassScanner.swift — Vision OCR + barcode detection.
  • Models/ — Flight, Airport, ParsedFlight.
  • Storage/ — SwiftData container + airport database loader.

~3,500 lines of SwiftUI + SceneKit across 24 files. Zero third-party dependencies. The hardest file in the project is BoardingPassPipeline.swift; the second hardest is the SceneKit great-circle math.
