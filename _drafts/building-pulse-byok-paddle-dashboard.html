Building Pulse: a BYOK Paddle revenue dashboard for iOS

I check my Paddle revenue about ten times a day. The web dashboard takes 3-4 seconds to load on a good connection, longer when I'm tethered, and the data I actually care about — how am I doing today vs the average? — is buried under three clicks and a date-picker that doesn't remember my last choice.

So I built Pulse: a native iOS app that talks to Paddle directly from the phone. Today / 7-day / 30-day windows, each with a comparison against the previous period of equal length, and Home + Lock screen widgets so I see the number without unlocking. Free on the App Store; the full Xcode source is $19 on Polar if you want to fork it.

This is the architecture writeup — what the app does, why it's structured the way it is, and the one piece of logic that took the longest to get right (cross-period comparison when the current period isn't done yet).

The BYOK choice

The first decision was the biggest: should the app proxy through a backend, or should it talk to Paddle directly?

Proxy means a backend service, an auth flow, a database to cache user keys, a privacy policy that's actually serious because you're holding a payment-provider API key, and a billing tier on the proxy itself the moment more than a handful of people use it.

Direct (BYOK = bring-your-own-key) means none of that. The user pastes their Paddle read-only API key into the app once. iOS Keychain holds it. Every request goes phone → Paddle. No backend, no auth, no DB.

The downsides are real: no shared device sync (each iPhone has its own key), no analytics on what users do (because there IS no backend), and the App Review reviewer needs a way to test the app without a real Paddle account. The first two I'm fine with — those are features, not bugs, for a tool that's about my revenue on my phone. The third one is solved with a demo-key pattern: a hard-coded sentinel value that, when entered, routes to a DemoPaddleClient returning fixture data. Apple G2.1(a) compliant; the reviewer never needs a real Paddle login.

The dashboard math

Every revenue dashboard does this period vs the previous period. The naïve implementation works fine for 7-day and 30-day windows: sum the last 7 days, sum the 7 days before that, divide, show the delta.

For today, the naïve implementation lies. If I check Pulse at 09:00, the "today" total covers 9 hours; the "yesterday" comparison covers all 24. Today will always look catastrophically bad until late evening.

The fix: compare today's first-9-hours against yesterday's same-first-9-hours, not against yesterday's whole day. The "displayed previous" value can still be yesterday's full total — that's what the human wants to see for context — but the percentage delta runs on equal-elapsed-time slices.

Here's the relevant chunk from RevenueAggregator.swift:

let cur = series(pair.current)
// For "today", compare against yesterday up to the SAME time of day
// so the % isn't misleadingly negative early in the day.
let prevRange: DateRange
if period == .today {
    let elapsed = now.timeIntervalSince(pair.current.from)
    prevRange = DateRange(from: pair.previous.from,
                          to: pair.previous.from.addingTimeInterval(elapsed))
} else {
    prevRange = pair.previous
}
let prev = series(prevRange)

Five lines, but they're the lines I cared about. Everything else in the app exists to put this in front of my eye in under a second.

On-device cache + incremental sync

Paddle's API returns transactions paginated. A pull of the last 30 days for a moderately active store is hundreds of requests if you ask one page at a time. Doing that on every app launch would chew through my Paddle rate limit and burn my battery.

So Pulse keeps a local 62-day cache (CoreData under the hood, accessed through a lightweight CachedTxn model). On launch it fetches only the transactions newer than the most recent cached billed_at. The first sync after install is the expensive one; everything after is incremental. The widgets read from the same cache, so they update instantly without making a network call.

The trade-off: if a refund or void happens to an OLD transaction (say, 45 days back), the cache won't notice until the next full sync. That's a known limitation. The Settings screen has a "rebuild cache" action that does a full pull when the data looks off.

The provider-agnostic seam

The Paddle Billing API surface lives behind one protocol:

protocol PaddleClient {
    func transactions(after: Date?) async throws -> [Txn]
    func subscriptions() async throws -> [Sub]
    // ... a handful more
}

Two implementations ship in the source bundle: PaddleClient (the real one) and DemoPaddleClient (the App Review fixture). The seam exists because I wanted to be able to swap providers without rewriting the UI — Stripe, Lemon Squeezy, or my own thing in the future, all the dashboard cares about is that something returns transactions and subscriptions.

If you fork Pulse and want to point it at Stripe instead, you write StripeClient: PaddleClient, change one line in the app's init to instantiate it, and the dashboard works. The math doesn't care.

Widgets are 90% of the value

Pulse's widgets are the feature I use most. Small widget shows today's number with the delta. Medium shows today + 7-day + 30-day with a tiny sparkline. They use WidgetKit + App Group, sharing the CoreData cache with the main app via AppGroupConstants.suiteName.

The trick to making widgets feel instant: the timeline provider doesn't fetch from Paddle. It reads from the cache, period. The main app handles refresh on its own schedule (and on every foreground); the widgets just render what's already there. Apple's relevantContexts hint helps the system show widgets at the right moment without you orchestrating it manually.

What I didn't build

No login, no user accounts, no cloud sync, no analytics (in the SaaS-tracking sense), no team features, no per-customer drill-downs beyond what fits in a single sheet, no notifications for big sales (yet — that's the obvious v1.1 add). The app is intentionally a read-only number-in-pocket tool. If you need more, the Paddle web dashboard is right there.

The whole codebase is ~2,800 lines of SwiftUI across 20 files. Zero third-party dependencies. It builds clean on a fresh Xcode install. The provider seam means most of it is reusable if you switch payment providers.

The structure, by folder

  • App/ — PulseApp + RootView. Boots the app, hands off to the main scene.
  • Features/Dashboard/ — Today / 7d / 30d cards + sparkline chart.
  • Features/Transactions/ — Searchable list + detail sheet.
  • Features/Onboarding/ — 3-step intro + Paddle key entry. Demo-key trigger lives here.
  • Features/Settings/ — Keychain key management, account add/switch, cache rebuild, language picker, about.
  • Models/PaddleModels.swift — Txn, Sub, RevenueWindow, RevenueType, etc.
  • Services/PaddleClient.swift + DemoPaddleClient.swift + RevenueAggregator.swift — The provider abstraction and the math.
  • Storage/ — Keychain wrapper, CoreData cache, App Group constants.
  • PulseWidget/ — Separate WidgetKit extension, shares Storage via App Group.

One file per concept. No clever inheritance. The hardest file in the whole project is RevenueAggregator.swift at ~200 lines.
